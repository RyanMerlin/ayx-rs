# Handoff Notes - 2026-06-18

Update: the `ayx-docs-schema` removal has been completed, and the temporary
Rust dashboard package has since been deleted. The notes below capture the
reasoning that led to those changes.

## Summary

Two decisions were discussed and should be picked up after reboot:

1. `ayx-docs-schema` appears to be unused workspace debt and is a candidate for removal.
2. The dashboard is large enough that the long-term pattern should likely be
   a standalone web app, with the CLI kept out of the delivery path.

## `ayx-docs-schema`

Current state:

- The crate only contains a single placeholder type: `CliSchema { version: &'static str }`.
- There are no imports or references to `ayx_docs_schema` or `docs-schema` anywhere else in the workspace.
- `cargo tree -i ayx-docs-schema` only shows the crate itself, which means nothing depends on it.

Recommendation:

- Remove the crate from the workspace unless there is a concrete near-term generator plan.
- If a schema artifact is needed later, generate it from `xtask` or directly from the clap tree instead of keeping a standalone crate around.

## Dashboard / CLI Web UI

Current state:

- The dashboard code was briefly extracted into a Rust package.
- It was a real web server, not a tiny helper: server-rendered HTML, embedded
  static assets, auth gating for remote mode, and multiple routes for
  overview/jobs/failures/workflows.
- It was no longer part of the `ayx` CLI surface by the time this note was
  handed off.

Recommendation:

- Keep the dashboard out of the CLI.
- Rebuild the dashboard in a true web language in a later phase.
- Share telemetry/profile logic through library code so the CLI and web app do not drift.

## Suggested Next Steps

1. Delete `ayx-docs-schema` from the workspace and update the lockfile.
2. Decide whether to rebuild the dashboard next or leave it shelved.
3. If rebuilding it later, define a small shared library boundary first so
   both the CLI and the standalone dashboard can reuse it.
