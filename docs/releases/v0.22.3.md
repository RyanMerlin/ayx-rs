# AYX-RS v0.22.3

Patch release that makes first-run Alteryx One sign-in recoverable and
diagnosable. It contains only this fix on top of v0.22.2.

## Highlights

- **Clear sign-in failures.** The email-passcode login ends by asking Alteryx
  One for an API access token. When that request is refused, the CLI now shows
  the HTTP status and the server's reason (redacted) instead of "PAT-mint
  outcome is unknown", and says what to do next:
  - 401: the session expired, so run `ayx one login` again.
  - 429: wait a minute, then log in again.
  - 403 and other refusals: use `ayx one login --oauth-api-token`, or ask a
    workspace admin to enable API access tokens.

  Only network failures and server errors (5xx) are still reported as
  "outcome unknown", now with their cause.
- **Onboarding finishes the job.** If the token request is refused,
  `ayx onboard` offers the OAuth API-token login immediately (Client ID and
  refresh token from the Alteryx One profile menu > API Tokens). It no longer
  reports "onboarding completed" when sign-in did not complete.
- **OAuth API tokens work on new profiles.** Profiles that set only a regional
  base URL (`https://us1.alteryxcloud.com`, `eu1`, ...) previously sent OAuth
  token requests to that API host, which is not the OAuth issuer, so
  `--oauth-api-token` login and token refresh failed. They now use the Alteryx
  One issuer. Existing saved credentials keep their keyring binding and do not
  need to be re-entered.
- **Actionable "not signed in".** A profile without credentials now fails with
  `auth_failed` and points to `ayx one login`, instead of an `internal` error.

## Upgrading

If `ayx onboard` or `ayx one login` failed for you on v0.22.2, upgrade and run
`ayx one login`. If it reports that the workspace refused the API access
token, run `ayx one login --oauth-api-token`.
